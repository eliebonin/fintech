# Tenant workspace and strategy alpha

The alpha begins with an authenticated actor's active tenant membership; it is not a support or platform-admin impersonation flow.

- `GET /v1/session/memberships` is available before a tenant is selected.
- `GET /v1/tenant-workspace` resolves the selected tenant's effective membership, enabled module codes, and separately held platform role.
- The console stores the selected tenant in the HttpOnly `active_tenant` cookie. Its value is HMAC-signed with `ACTIVE_TENANT_COOKIE_SECRET`; production must configure that secret. Local development uses a development-only fallback secret.
- `POST /api/session/active-tenant` validates the candidate against upstream memberships before setting the cookie and marks a context change with `X-Tenant-Context-Changed: 1`.
- The `/tenant-profile` screen is the authoritative UI for the active tenant's identity, the user's membership role, and enabled modules. The switcher changes context; it does not manage tenant settings.
- The `/strategies` console uses that server-side tenant context. Strategy creation is shown only to tenant administrators with `TRADING` or `FUND_MANAGEMENT` entitlement.
- `/instruments` is the dedicated tenant-scoped catalogue. It resolves the active server-side tenant context for the initial catalogue request and browser search BFF request. It labels the current catalogue as `CANONICAL`; tenant-owned custom instruments are intentionally the next vertical slice and will be visibly separate rather than silently mixed with canonical records.
- `/instruments/create` is the single creation launchpad. It groups existing specialist instrument forms by economic type and does not present listings or index families as economic instruments. Listings remain a follow-on action against an approved instrument; index families remain supporting reference structure.
- `/instruments/requests` is an instrument-only pending-review view. It filters the tenant's work queue to pending economic-instrument creation proposals and explicitly excludes mappings, market data, NAV, listings, and index-family setup. Queue records now carry a `proposalType` so that filtering is based on workflow data rather than display text.
- The sidebar has one `Instruments` destination rather than a separate reference-data action list. The catalogue header provides the `Requests` and `Create instrument` actions.
- `/operations` is the tenant-scoped, cross-module review inbox and has a permanent sidebar destination. It presents counts, a filter, and a full actionable queue for reference-data, mapping, NAV, and market-data decisions; listings therefore appear there rather than being mixed into the instrument-creation request list. This applies Cloudscape's guidance that a dashboard overview should link to a detailed resource list rather than carry the full operational list itself ([Dashboard items](https://cloudscape.design/patterns/general/service-dashboard/dashboard-items/)), and that common global actions should be available from the relevant global page ([Actions](https://cloudscape.design/patterns/general/actions/)). The sidebar retains only durable primary workspaces, consistent with Cloudscape's advice not to turn side navigation into a sitemap ([Service navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)).
- The catalogue is intentionally table-first: its overview displays only name, type, base currency, status, and listing count; users open the dedicated detail route for the full record. This follows Cloudscape's guidance that tables suit larger collections whose shared attributes must be scanned and compared ([View resources](https://cloudscape.design/patterns/resource-management/view/)). Search remains visible and the first filters are type and status, matching its recommendation to use simple collection filters when users commonly narrow by one or two properties ([Filtering patterns](https://cloudscape.design/patterns/general/filter-patterns/)). The page does not retain a permanently visible detail panel: Cloudscape advises that split panels are for in-context monitoring or troubleshooting and do not replace a dedicated details page ([Split view](https://cloudscape.design/patterns/resource-management/view/split-view/)).
- Catalogue search and pagination are server-backed. The initial view and every changed query, type, status, or page size request a bounded page from `/v1/instruments/search`; the BFF validates `limit` to 1–100 and non-negative `offset` before forwarding the request. The response `meta.total` is the authoritative result count, so the UI never estimates catalogue size from the current browser page.
- The default page size is 25, with 50 and 100 as explicit alternatives. The UI displays the current range, total, numbered navigation, and first/last controls. This follows Cloudscape's table-view guidance to use pagination for large resource sets because it makes sections revisit-able and represents the collection size accurately ([Table view: pagination](https://cloudscape.design/patterns/resource-management/view/table-view/)). Infinite/progressive loading is intentionally not used: that pattern is recommended where users must compare a large set continuously in one view, which is not the primary instrument-discovery workflow.
- Text search is debounced for 300 ms and then runs against the server, rather than loading the whole catalogue into the browser or waiting several seconds after input. Search, type, and status changes reset to the first page; their result count and pagination therefore refer to the same query. Search covers the API's governed search predicate (canonical name, identifiers, listing and provider-facing codes) while the UI's type/status selectors map to server query parameters. This preserves tenant visibility enforcement at the API boundary.
- Instrument lifecycle requests retain the server-assigned submitter account ID inside the immutable proposed payload and now expose it, the proposal timestamp, type, status, and review route in the instrument-only queue. The steward review route resolves the active tenant session, rather than a legacy local tenant context. The workflow requires a decision reason and preserves decision evidence; approval materialises canonical rows and rejection leaves no canonical instrument. This follows OWASP's guidance that attributable business decisions record who, what, when, action, outcome, and reason ([Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)); NIST frames this as an audit-and-accountability control ([SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final)).
- The review screen makes the lifecycle legible as `Submitted → Pending review → Approved | Rejected`. On approval it gives the steward a direct route to the materialised instrument when a canonical reference node exists; on rejection it keeps the recorded reason and decision evidence visible on the immutable review record, then offers a return to the pending instrument-request queue. Rejected items are intentionally not reintroduced into that pending queue: the review record is the authoritative audit view.
- Listing creation has two intentionally complementary entry points. The primary route starts from a canonical instrument detail page at `/instruments/{instrumentId}/listings/new`, preserving and displaying the selected parent while allowing an explicit `Change instrument` escape hatch. The global `/instruments/listings/new` route remains search-first for operations users who begin from an external ticket or exception. This follows Cloudscape guidance to make resource-relevant actions available from the resource landing page ([Service navigation](https://cloudscape.design/patterns/general/service-navigation/side-navigation/)) and to preserve parent context for a related sub-resource while retaining a full-page fallback for independent, complex work ([Sub-resource create](https://cloudscape.design/patterns/resource-management/create/sub-resource-create/)). The dedicated page is appropriate because a listing has its own validation, duplicate detection, and venue-specific attributes.
- Listed cash trade booking is now an alpha vertical slice. An active listing exposes `Book trade`, which opens `/trades/new?listingId={listingId}`. The server resolves that exact listing under the signed active-tenant session and locks the listing, trading currency, and execution venue; a tenant administrator with `TRADING` then chooses an active strategy and records BUY/SELL, positive quantity, positive execution price, an offset-bearing execution timestamp, and settlement date. The browser never supplies tenant or user headers; its same-origin BFF derives them from the active session and forwards an `Idempotency-Key` to the API. The API records an immutable `BOOKED` trade, its initial lifecycle event, derived listing facts, optional source reference/comment, and a durable tenant-scoped idempotency fingerprint. Retrying the unchanged ticket returns the original trade; reusing the key with changed content conflicts. The trade detail page displays the derived direction, booking actor, venue, and lifecycle evidence.
- This is deliberately limited to manual, already-executed, listing-backed cash trades (equity/ETP-style). It excludes order management, fills/allocation workflows, amendment/cancel/correct lifecycle events, fees, broker/trader/tag selection, entitlement-aware counterparty selection, FX/derivatives/funds/OTC booking, position validation, valuation, and P&L calculation. Those remain later modules, not hidden form fields. The boundary follows the controls documented in the design specification, including ESMA’s [MiFID II transaction-reporting guidance](https://www.esma.europa.eu/sites/default/files/library/esma65-8-2594_mifir_data_reporting_qas.pdf), the FCA’s [transaction-reporting page](https://www.fca.org.uk/markets/markets-reporting/transaction-reporting), and the SEC’s [books-and-records requirements](https://www.ecfr.gov/current/title-17/chapter-II/part-240/section-240.17a-3).

This remains an alpha boundary: the demo actor environment seam is still used, and existing legacy pages have not yet been migrated from their static demo tenant context. The next hardening pass must add end-to-end identity integration, mutation idempotency, audit events, and broader browser/API tests.
