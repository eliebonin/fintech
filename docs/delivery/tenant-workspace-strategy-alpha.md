# Tenant workspace and strategy alpha

The alpha begins with an authenticated actor's active tenant membership; it is not a support or platform-admin impersonation flow.

- `GET /v1/session/memberships` is available before a tenant is selected.
- `GET /v1/tenant-workspace` resolves the selected tenant's effective membership, enabled module codes, and separately held platform role.
- The console stores the selected tenant in the HttpOnly `active_tenant` cookie. Its value is HMAC-signed with `ACTIVE_TENANT_COOKIE_SECRET`; production must configure that secret. Local development uses a development-only fallback secret.
- `POST /api/session/active-tenant` validates the candidate against upstream memberships before setting the cookie and marks a context change with `X-Tenant-Context-Changed: 1`.
- The `/tenant-profile` screen is the authoritative UI for the active tenant's identity, the user's membership role, and enabled modules. The switcher changes context; it does not manage tenant settings.
- The `/strategies` console uses that server-side tenant context. Strategy creation is shown only to tenant administrators with `TRADING` or `FUND_MANAGEMENT` entitlement.
- `/instruments` is the dedicated tenant-scoped catalogue. It resolves the active server-side tenant context for the initial catalogue request and browser search BFF request. It labels the current catalogue as `CANONICAL`; tenant-owned custom instruments are intentionally the next vertical slice and will be visibly separate rather than silently mixed with canonical records.
- `/instruments/create` is the single creation launchpad. It groups existing specialist instrument forms by economic type and does not present listings or index families as economic instruments. Listings remain a follow-on action against an approved instrument; index families remain supporting reference structure.
- `/instruments/requests` is an instrument-only pending-review view. It filters the tenant's work queue to pending economic-instrument creation proposals and explicitly excludes mappings, market data, NAV, listings, and index-family setup. Queue records now carry a `proposalType` so that filtering is based on workflow data rather than display text.
- The sidebar has one `Instruments` destination rather than a separate reference-data action list. The catalogue header provides the `Requests` and `Create instrument` actions.
- The catalogue is intentionally table-first: its overview displays only name, type, base currency, status, and listing count; users open the dedicated detail route for the full record. This follows Cloudscape's guidance that tables suit larger collections whose shared attributes must be scanned and compared ([View resources](https://cloudscape.design/patterns/resource-management/view/)). Search remains visible and the first filters are type and status, matching its recommendation to use simple collection filters when users commonly narrow by one or two properties ([Filtering patterns](https://cloudscape.design/patterns/general/filter-patterns/)). The page does not retain a permanently visible detail panel: Cloudscape advises that split panels are for in-context monitoring or troubleshooting and do not replace a dedicated details page ([Split view](https://cloudscape.design/patterns/resource-management/view/split-view/)).

This remains an alpha boundary: the demo actor environment seam is still used, and existing legacy pages have not yet been migrated from their static demo tenant context. The next hardening pass must add end-to-end identity integration, mutation idempotency, audit events, and broader browser/API tests.
