# Structured informational lifecycle notices — 11 November 2026

## Use in the portal
Under **Strategy → Overview → Lifecycle assistance → Structured product schedules**, select **Tier1 · Notifications**. Manual0 remains the default. The tenant needs lifecycle notification access and the user needs scoped LIFECYCLE_READ; configuring the selection requires existing configure authority. No subscription, positive selection or permission is added automatically.

Open **Lifecycle**, choose **Structured product schedules** or **All events**, and apply the strategy, instrument and date filters. **Inspect schedule** opens the existing modal side panel, preserving filters, pagination and keyboard focus. Technical identities are collapsed. Conditions and exact decimal thresholds remain available without dominating the contract facts.

Source-linked coupon observations, eligible potential-autocall observations, final valuation and contractual maturity are shown. Before-first-autocall observations and missing eligibility are explicit. Related payment dates are conditional source information. A passed date is labelled **Date passed · outcome not assessed**, never overdue/unpaid/triggered. Every structured row has INFORMATION relevance, including unavailable sources or unknown position evidence. It does not become a financial publication blocker.

Direct structured holdings and structured performance references of held swaps are covered. Inspection distinguishes the held instrument, its signed units/nominal and quote/price currency from the observed structured contract. No underlying position or swap termination is inferred. Past event context uses known holdings at that date; future event context uses current holdings. Flat/cancelled holdings are excluded, and separate nonzero allocation buckets survive an aggregate zero quantity.

## Implementation and deliberate limits
- [Domain reader](../../lifecycle/worklist_structured.py) combines scoped held candidates, immutable ledger/allocation reconstruction and current source-linked schedules before relevance/status/count/pagination. Request-local source caching avoids reloading one contract for each strategy. Search includes authorised held/observed names and identifiers.
- [Shared terms source projection](../../security_master_schema/instrument_terms_schedule.py) was moved below HTTP without changing the reader function or its existing response contract. The [HTTP import surface](../../apps/reference_api/instrument_terms_schedule.py) remains compatible. Discovery uses current condition/coupon/component links, excluding owner-only historical schedules, retired/cancelled child links/actions, and payment/reset rows that must not be relabelled as observations.
- Current versus original BOOKED swap performance-reference conflicts yield unavailable information instead of presenting a changed reference as the original contract. This conservative comparison includes retained earlier booking episodes. No reference-change/reset lifecycle is implemented.
- Current approved sources applied to historical dates are not historical source-knowledge snapshots. Complex chains beyond the existing depth bound, missing/private references and cycles remain unassessed. Inaccessible names and IDs are not included in notices/inspection.
- Stored thresholds, operators, basis, inclusivity, aggregation and conditional actions are displayed without a new payoff or percentage interpretation. Continuous barriers remain source terms; no daily observation is invented.
- Notifications use the requested date window; **Include open overdue events** does not expand structured history. Missing-source notices have no inferred event date. Future observations after a held swap's own sourced maturity are excluded for relevance; that filter does not close the swap.
- A scheduled date proves no fixing, barrier result, coupon entitlement, autocall, payment or termination. A later scheduled observation may remain visible until a confirmed outcome is implemented and the source/ledger is updated. No persisted acknowledgement/assignment/delivery queue is introduced.
- No preparation, booking, cash, outcome recording, market-data evaluation or valuation change. Independent selections support0/1 only, even under commercial Tier3. Existing handlers for bond/FX financial closure remain separate.

[GET adapter](../../apps/reference_api/lifecycle_worklist_routes.py), [BFF](../../apps/ops-console/src/app/api/lifecycle/%5B...segments%5D/route.ts) and [inspector](../../apps/ops-console/src/features/lifecycle-worklist/structured-inspection.tsx) retain tenant-header checks, strategy scope, allowlisted query inputs, GET-only routing, stale-source rejection and obsolete-read aborts. [Migration115](../../alembic/versions/20261111_115_structured_informational_notifications.py) extends the retained strategy assistance constraint; it creates no financial tables, grants or defaults.

[Specification and opened research](../superpowers/specs/2026-11-11-structured-informational-notifications.md) records source distinctions and product-specific limitations. [Execution plan](../superpowers/plans/2026-11-11-structured-informational-notifications.md) tracks verification.

## Read-timeout correction — 11 November 2026

**Superseded mitigation:** the scalar cache described below was subsequently replaced by [batched source reads](structured-lifecycle-batch-reads-20261111.md), measured at89 queries/1.310-second median with complete result/proof parity. The old cache class is no longer part of product code.

After structured notifications were enabled for FCPGF, the full87-root source/holding assessment returned270 notices but exceeded the shared10-second frontend read deadline. The old BFF fallback also incorrectly instructed a read-only user to retry a booking key.

`TermsScheduleReadCache` now reuses visible-reference identities and type/issuer/currency labels within one connection, tenant and transaction. It is created per worklist read, is never global, rejects reuse in a different scope, and does not cache permissions, negative visibility, complete source rows or financial calculations. New requests see current sources. Existing source fingerprints, active/private-reference checks, allocation reconstruction, full-population filtering/counts and pagination remain unchanged.

A fixed-cutoff, read-only comparison against the retained original reader returned identical complete results:270 notices (266 upcoming,4 date-passed), with4458→2258 queries and14.864→7.307 seconds in that comparison. These are local observations under the test workload, not a production latency guarantee. Source fact tables are still read per contract; broader bulk loading remains a potential scalability improvement.

Only GET `/api/lifecycle/worklist` uses a bounded30-second deadline, with the existing45-second browser deadline outside it. Small reads keep their existing configured deadline (default10seconds); financial writes retain35seconds and stable-key/uncertain-outcome controls. Read failures now offer applied-filter retry without booking instructions.

Verification:27 affected backend cases passed in disposable PostgreSQL;10 lightweight source/scope rules passed;19 focused BFF/read/client tests and TypeScript passed. The new cases check complete projection parity, private dependencies and tenant/connection/transaction cache boundaries. Existing groups overlap and are not additive unique coverage. The initial failing read-message/cache/deadline regressions were observed before implementation.
