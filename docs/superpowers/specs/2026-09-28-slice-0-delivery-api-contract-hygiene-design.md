# Slice 0: Delivery and API Contract Hygiene Design

**Status:** Proposed for review  
**Date:** 2026-09-28  
**Scope:** Reference Data API, Ops Console, workspace delivery controls

## Goal

Make the existing Reference Data API consumable and safely deliverable as an
explicit versioned interface. The slice establishes a reproducible OpenAPI
contract, generated TypeScript consumer surface, consistent safe errors, and
the minimum automated delivery and secret/log controls needed before broader
API or UI work continues.

Success means a developer or CI run can prove that the checked-in TypeScript
surface matches the API, expected API failures have one documented shape, and
the principal Python and TypeScript quality checks run without granting a
workflow unnecessary authority or exposing credentials in the repository.

## Scope

This slice changes only the delivery/API boundary of the existing reference
data application:

1. export and version the FastAPI OpenAPI 3.1 contract;
2. generate TypeScript schema types and a typed fetch client from that
   contract, then move the Ops Console onto that public package surface;
3. return RFC 9457 problem details for expected, validation, and unhandled
   API errors, with a correlation identifier on every response;
4. add a least-privilege GitHub Actions quality workflow and deterministic
   dependency inputs; and
5. prevent runtime logs and real credentials from being treated as source,
   and scan committed content for common secret patterns.

The work is intentionally not an authentication, tenancy-isolation, database
routing, authorisation, rate-limiting, request-size, observability-platform,
or production-deployment implementation. In particular, trusted development
headers and the existing development fixture seam remain separate security
work; this slice must not represent them as production controls.

## Contract design

### Contract source and versioning

`apps/reference_api/main.py` remains the sole API schema source. A deterministic
script at `scripts/export_openapi_contract.py` imports the application and
writes `packages/api-contracts/openapi/reference-data-api.v1.json` using
`app.openapi()` without starting a server or connecting to a database. The
artifact is formatted deterministically, checked into source control, and
retains FastAPI's OpenAPI 3.1 output.

The contract version is the API's major path version (`v1`) rather than an
independent incompatible version. Additive endpoints and fields update the
same artifact; incompatible changes require an explicit `v2` API path and
separate artifact. The API's information block names the service, its
version, and the stable versioned server/path convention.

The export command supports a check mode. CI regenerates the contract and
fails if regeneration changes a committed artifact. A human must therefore
review every interface change in both route code and the generated contract
diff.

### Generated TypeScript package

`packages/api-contracts` becomes a workspace package with three public
surfaces:

* the committed OpenAPI JSON artifact;
* `src/generated.ts`, generated solely by `openapi-typescript` from that
  artifact; and
* `src/client.ts`, a small typed `openapi-fetch` wrapper that creates a
  client from the generated `paths` type and receives its base URL and fetch
  implementation as explicit configuration.

`src/index.ts` exposes the generated types and client factory. Generated
files contain a clear "do not edit" header and are regenerated by one
workspace script. The handwritten wrapper contains no route-specific request
or response models; it is the stable, testable transport seam around the
generated schema types.

The Ops Console imports endpoint request/response types and the client from
this package rather than maintaining duplicate definitions in
`apps/ops-console/src/lib/reference-api-types.ts`. Any local adapter retained
by the console is limited to UI presentation and cannot redefine API payload
shapes. A TypeScript consumer test proves a representative `GET` and a
mutation call type-check through the generated client.

## Error and correlation contract

All HTTP errors from `apps/reference_api` use the RFC 9457
`application/problem+json` representation:

```json
{
  "type": "https://api.fortem.local/problems/request-validation",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more request fields are invalid.",
  "instance": "/v1/example",
  "code": "request.validation_failed",
  "requestId": "uuid"
}
```

`type`, `title`, `status`, `detail`, and `instance` follow the standard;
`code` and `requestId` are documented extension members. `type` URIs resolve
to static repository documentation or an API documentation page before they
are emitted publicly. The API must declare the reusable problem schema and
common 4xx/5xx responses in OpenAPI, so generated consumers see the error
shape rather than an undocumented exception.

An HTTP problem abstraction represents expected domain/transport failures.
Handlers normalise FastAPI/Starlette HTTP exceptions and request validation
exceptions. Validation errors may expose safe field locations and messages in
an `errors` extension, but never rejected values, submitted bodies, headers,
tokens, database URLs, stack traces, or raw internal exception text.

A top-level unhandled-exception handler logs server-side diagnostic context
with the request ID and returns only a generic 500 problem. Each response,
including success and errors, includes `X-Request-ID`. A valid caller-supplied
request ID may be reused; otherwise the API creates a UUID. Request IDs are
not authentication or tenant identifiers.

## Logging and secret hygiene

Application logging uses a single configured logger with structured or
key-value fields for request ID, HTTP method, route template, status, and
duration. It must not log request/response bodies, authorisation headers,
cookies, database connection strings, tokens, or secrets. Server exceptions
are logged with stack traces only at the server boundary and retain the same
request ID returned to the caller.

`.gitignore` ignores `*.log` and a `logs/` directory in addition to current
local environment files. Existing untracked runtime logs are left untouched;
they are not source artefacts and are not deleted by this slice.

`.env.example` contains only explicit placeholders and safe local defaults;
it must never contain a reusable password, token, connection string with
credentials, or production hostname. Runtime configuration remains supplied
outside version control.

The GitHub workflow runs Gitleaks through a full-commit-SHA-pinned action with
redacted output and a committed minimal configuration/allowlist only for
deliberate non-secret test placeholders. GitHub Secret Scanning and Push
Protection are additionally documented as repository/organisation settings
for an administrator to enable. They are not represented as being enabled by
source code, and the project must not bypass a push-protection finding merely
because a value is described as test data.

## Deterministic dependencies and CI

The current permissive Python ranges become human-maintained input
requirements and a committed, fully resolved, hash-verified lock file.
Python CI installs only from that lock with `--require-hashes`. The project
pins its CI Python runtime to one supported minor version. The lock is
generated for that runtime and Linux CI platform; a future cross-platform
runtime policy must add the appropriate hashes/locks explicitly rather than
assuming one lock works everywhere. The experimental `pip lock` command is
not the lock-file authority for this slice.

The existing `pnpm-lock.yaml` is authoritative for Node dependencies. CI uses
the workspace package-manager version and `pnpm install --frozen-lockfile`.
Code-generation dependencies are declared in the workspace manifest and lock
file, never fetched ad hoc by a workflow command.

Add `.github/workflows/quality.yml`, running for pull requests and pushes to
the default branch. It has `permissions: contents: read`, does not use
`pull_request_target`, does not expose repository secrets to pull-request
code, and uses only full-commit-SHA-pinned external actions. Cache only
package-manager artifacts with cache keys derived from the committed lock
files; never cache virtual environments, credentials, `.env` files, or build
outputs containing runtime data.

The required jobs are:

1. **Python/API:** install locked dependencies, compile the project, export
   OpenAPI and fail on drift, then run the Python test suite.
2. **Web/contract:** install with frozen pnpm lock, regenerate TypeScript and
   fail on drift, type-check, test, and build the Ops Console.
3. **Secret scan:** run the redacted Gitleaks scan against repository content.

The workflow is intentionally a quality gate, not a deployment workflow. It
does not publish artefacts, write releases, access cloud accounts, or use
environment secrets.

## Verification

The implementation must add tests before the corresponding production code
for:

* deterministic contract export and package generation;
* OpenAPI declaration of the reusable problem schema and representative error
  responses;
* normalisation of an expected HTTP error, a validation failure, and an
  unhandled exception, including media type, safe body and `X-Request-ID`;
* no leakage of a raw exception message or invalid submitted value; and
* typed consumption of representative API calls in the Ops Console.

Before completion, run the full Python test suite, contract export/generation
drift checks, Ops Console type-check/test/build, and the secret scan. Document
the exact commands and results in a dated quality-review note under
`docs/delivery/quality-reviews/` and update the delivery index if needed.

## Acceptance criteria

The slice is complete only when all of the following are true:

* `reference-data-api.v1.json` is committed, deterministic, and generated
  directly from the FastAPI application;
* generated TypeScript types and the typed client are committed, importable by
  the Ops Console, and cannot silently drift from the contract in CI;
* all documented API failure paths return one RFC 9457-compatible response
  model and every response has a request ID;
* raw exception details and rejected sensitive values never reach API clients
  or normal request logs;
* the quality workflow is least-privilege, SHA-pinned, lock-file driven, and
  covers Python, contract, web, and secret checks;
* logs and real environment credentials are excluded from source; and
* verification evidence and remaining limitations are documented.

## Explicit deferrals

This slice does not add API authentication, authorisation, tenant routing,
row-level security, per-client rate limits, request-size limits, distributed
tracing, external log aggregation, dependency-update automation, SBOMs,
container signing, vulnerability remediation SLAs, or a production secrets
manager. Each remains necessary follow-on work, but none is silently implied
by the controls defined here.
